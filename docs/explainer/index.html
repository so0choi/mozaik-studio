얼굴 모자이크 스튜디오는 어떻게 동작하나

영상 처리를 처음 보는 웹·백엔드 개발자를 위한 해설. 업로드한 영상이 모자이크된 결과 파일이 되기까지 어떤 서비스가 무엇을 하는지, 그 사이에 쓰인 영상·컴퓨터 비전 개념을 실제 코드 위치와 함께 정리했다.

한 문장 요약: 워커가 영상을 일정한 프레임 간격으로 다시 만들고(정규화), 프레임마다 얼굴 위치를 찾은 뒤(검출), 같은 얼굴끼리 이어 "트랙"을 만든다(추적). 사용자는 브라우저에서 트랙 단위로 보이기/가리기를 고르고, 워커가 같은 규칙으로 픽셀화해 결과 영상을 만든다. 기본값은 전부 가림이다.

1전체 흐름

서비스 4개와 공유 디렉터리 1개. 서로는 HTTP, Redis 리스트, 파일로만 이야기한다.

작업 상태 전이

2따라가기 위해 필요한 영상 기초

이 프로젝트의 모든 좌표와 편집은 "몇 번째 프레임인가"로 표현된다. 그래서 프레임 번호가 흔들리지 않게 만드는 것이 첫 단계다.

프레임과 fps

영상은 정지 이미지(프레임)의 연속이다. fps(frames per second)는 1초에 몇 장인지. 30fps 영상의 1.5초 지점은 45번째 프레임이다.

웹과 워커는 같은 공식으로 프레임 번호를 구한다: frame = round(시각 × fps). 웹은 apps/web/src/lib/frames.ts의 frameAt().

코덱과 컨테이너

컨테이너(mp4, mov, mkv)는 상자, 코덱(H.264, AAC)은 상자 안 내용물을 압축한 방식이다. 같은 .mp4라도 안의 코덱은 다를 수 있다.

정규화 결과는 항상 mp4 + H.264 영상 + AAC 오디오. 브라우저 <video>, OpenCV, ffmpeg가 모두 확실히 읽는 조합이다.

왜 CFR로 바꾸나 (고정 vs 가변 프레임레이트)

가변 프레임레이트(VFR) 영상에서는 브라우저가 1.5초에 보여주는 프레임과 OpenCV가 45번째로 읽는 프레임이 다를 수 있다. 그러면 미리보기에서는 가려졌던 얼굴이 결과 영상에서는 한 프레임 어긋나 드러난다. 그래서 워커는 맨 처음 원본을 원본 fps의 반올림 값으로 다시 인코딩한다(고정 프레임레이트, CFR).

PTS는 0부터

PTS(presentation timestamp)는 프레임마다 붙은 "이 프레임을 몇 초에 보여줘라" 값이다. 원본 파일은 0.033초나 1.2초에서 시작하기도 한다.

  • setpts=PTS-STARTPTS, asetpts=PTS-STARTPTS: 영상·오디오 첫 시각을 0으로 당김
  • -avoid_negative_ts make_zero: 음수 시각 방지
  • -bf 0: B-프레임을 쓰지 않음. 쓰면 mp4 edit list 때문에 첫 표시 시각이 0.04–0.07초가 된다 (normalize.py 주석)

그래야 브라우저의 currentTime = 0이 프레임 0이 된다.

오디오는 normalized.mp4에서 복사

렌더는 OpenCV로 프레임을 읽어 픽셀화한 뒤, 원시 픽셀을 ffmpeg stdin으로 흘려 새로 인코딩한다. OpenCV는 오디오를 다루지 않으므로 오디오는 따로 붙인다.

이때 원본이 아니라 normalized.mp4의 오디오를 -c:a copy(재인코딩 없이 그대로)로 넣는다. 정규화에서 영상과 오디오의 시작을 함께 0으로 맞췄기 때문에, 원본 오디오를 쓰면 시작 오프셋만큼 입 모양과 소리가 어긋날 수 있다 (리뷰 R3-9).

render.py: -i - (rawvideo) -i normalized.mp4 -map 0:v -map 1:a -c:a copy -shortest

정규화에서 같이 하는 것: ffmpeg 출력을 파싱해 길이·해상도를 검사한다(30분, 4K 초과면 failed + "30분 이하, 4K 이하 영상만 지원합니다."). 결과는 meta.json {fps, width, height, frameCount, durationSec, hasAudio}. 오디오가 없으면 -an으로 만들고 렌더에서도 오디오 단계를 건너뛴다.

3얼굴 검출: YuNet

"이 한 장의 이미지 안에서 얼굴이 어디 있나"만 답한다. 프레임끼리의 연결은 다음 절의 추적이 한다.

무엇을 쓰나

OpenCV의 cv2.FaceDetectorYN에 YuNet ONNX 모델(face_detection_yunet_2023mar.onnx)을 얹어 CPU로 돌린다. 작고 빠른 신경망 검출기다.

입력은 프레임 한 장, 출력은 얼굴마다 [x, y, w, h, 눈·코·입 좌표 10개, score]. 이 프로젝트는 박스와 점수만 쓴다.

짧은 변이 1080보다 크면(4K 등) 1080으로 줄여 검출하고 좌표를 원본 해상도로 되돌린다.

worker/mosaic_worker/detect.py — FaceDetector.detect()

신뢰도 점수(confidence)와 0.5

점수는 0–1 사이의 "얼굴일 것 같은 정도"다. 확률처럼 보이지만 모델 내부 값이며, 같은 얼굴도 프레임마다 0.9 → 0.55 → 0.9처럼 흔들린다. 옆얼굴, 손으로 가린 얼굴, 먹는 중인 얼굴은 낮게 나온다.

score_threshold = 0.5
이보다 낮은 후보는 검출기가 아예 내지 않는다. 낮게 잡아 진짜 얼굴을 덜 놓치고, 오탐은 추적 규칙(0.6)에서 거른다.
nms_threshold = 0.3
같은 얼굴에 겹친 후보 박스가 여러 개 나오면 IoU 0.3 넘게 겹치는 것 중 점수 높은 하나만 남긴다(NMS).
검출 ≠ 인식. 검출(detection)은 "여기 얼굴이 있다", 인식(recognition)은 "이 얼굴은 누구다"이다. 이 시스템은 얼굴 특징 벡터(임베딩)를 만들지 않고 ReID도 쓰지 않는다. 그래서 같은 사람이 화면을 나갔다 들어오면 다른 트랙이 되고, 사람이 직접 "같은 사람으로 묶기"로 합친다. 생체정보 처리를 피하기 위한 의도된 설계다 (스펙 §2, §3.5).

4추적: 직접 구현한 ByteTrack식 추적기

검출은 프레임마다 "박스 몇 개"를 줄 뿐 이름표가 없다. 추적기는 "프레임 N의 이 박스는 프레임 N-1의 t3과 같은 얼굴"을 정해 트랙 ID를 붙인다. 외형은 보지 않고 위치와 크기만 본다.

worker/mosaic_worker/tracker.py — Tracker.update()(프레임마다), Tracker.finish()(끝에 한 번)

IoU: 두 박스가 얼마나 겹치나

IoU = 겹친 넓이 ÷ 합친 넓이. 완전히 같으면 1, 안 겹치면 0. 추적기는 트랙의 예측 위치와 새 검출의 IoU가 0.3 이상이면 같은 얼굴 후보로 본다.

왜 트랙이 조각나나

외형을 보지 않으므로 다음 중 하나면 같은 사람이 새 ID를 받는다.

  • 0.5초보다 길게 가려지거나 화면 밖으로 나감
  • 빠르게 움직여 강제 분리 조건에 걸림
  • 컷 전환으로 위치가 갑자기 바뀜

이건 실패가 아니라 설계의 대가다. 사람 카드에 "조각 수"가 보이고, 사용자가 카드를 여러 개 골라 같은 사람으로 묶기(edits.groups)로 합친다. 반대 방향 실수(두 사람이 한 트랙)는 트랙 분할로 고친다(6절).

방금 고친 오탐 버그

원래 2단계에서 짝을 못 찾은 저점수 검출도 새 트랙을 시작했다. 음식·손·질감이 0.5–0.6 점수로 한 프레임 잡히면 새 "사람"이 되고, gap-hold 때문에 0.5초짜리 모자이크가 화면 곳곳에 생겼다. 검수 항목도 그만큼 늘었다.

5모자이크 렌더

모자이크(픽셀화)는 박스 영역을 블록 단위로 나눠 블록마다 평균색 하나로 칠하는 것이다. 핵심은 미리보기와 결과 영상이 같은 블록 격자를 쓰는 것.

블록 크기 규칙

트랙
blockSize = max(8, 트랙 박스 짧은 변의 중앙값 // 8). 트랙 전체에서 한 번 계산(tracker.py block_size()). 프레임마다 바꾸면 모자이크가 꿈틀거린다.
수동 박스
max(8, min(w, h) // 8), 박스마다 계산.

어떤 박스를 가리나

tracks.json + edits.json + manual/*.json을 합쳐 {frame: [[x,y,w,h,block], ...]}을 만든다. 기본은 전부 가림, visible에 있는 트랙·그룹 조각만 뺀다. 분할된 트랙은 t2a/t2b 조각 단위로 판단한다.

6검수 큐, 트랙 분할, 수동 박스

자동 결과가 틀리기 쉬운 지점을 워커가 미리 표시하고, 사람이 확인하거나 고친다. 확인하지 않으면 렌더할 수 없다.

확인 필요 항목 (review.json)

low_confidence

실제 검출 프레임 15개를 미끄러지는 창으로 보며 평균 점수가 0.6 미만인 구간(15프레임 이상). 오탐이거나, 진짜 얼굴인데 박스가 불안한 곳.

gap

gap-hold로 채운 구간. 예측 위치가 실제 얼굴을 덮었는지 사람이 봐야 한다.

crossing

두 트랙 박스의 IoU가 0.1을 넘는 구간. 교차 후 ID가 바뀌었는지 확인한다.

같은 종류·같은 트랙의 항목이 1초 이내로 붙어 있으면 하나로 합친다. 항목마다 "괜찮음"(→ edits.reviewed에 추가) 또는 "박스 추가"를 고른다. worker/mosaic_worker/review.py build_review()

트랙 분할

추적기가 두 사람을 한 트랙으로 이었을 때, 현재 프레임 F에서 "여기서 분할"하면 edits.splits에 {trackId: "t2", frame: F}가 들어간다.

t2  ─────────────┬───────────────
                 F
t2a ─────────────┘  (frame < F)
t2b              └─────────────── (frame ≥ F)

원본 tracks.json은 그대로 두고, 웹(pieces.ts)과 워커(compose.py split_fragments())가 읽을 때 나눈다. 보임/가림은 조각 ID로 지정한다.

수동 박스와 CSRT 전파

검출기가 놓친 얼굴은 사용자가 플레이어에서 박스를 그린다. 웹이 POST /manual → API가 queue:propagate → 워커가 OpenCV CSRT 추적기로 앞뒤로 따라간다.

  • CSRT는 "처음 지정한 영역의 생김새"를 학습해 다음 프레임에서 찾는 단일 물체 추적기다. 검출기 없이도 따라가지만, 실패 신호 없이 서서히 어긋날 수 있다.
  • 속도를 위해 짧은 변 720으로 줄인 프레임에서 추적, 방향별 최대 10초, 실패하거나 화면을 벗어나면 중단
  • 결과는 25% 확장해 manual/{id}.json에 저장. 상태는 job:{id}:manual:{mid} (tracking → done|failed)
  • 재기준(re-anchor): 다른 프레임에 박스를 다시 그리면 가장 가까운 이웃 기준 프레임 사이만 교체
  • 전파가 실패하거나 아직 없으면, 그린 프레임만 고정 박스로 가린다 (웹·워커 동일)

worker/mosaic_worker/propagate.py propagate()

YuNet 트랙 vs CSRT 수동 박스: 자동 트랙은 "매 프레임 검출 → 위치로 잇기"라 외형을 기억하지 않는다. CSRT는 한 영역의 외형을 기억해 따라가는 방식이다. 그래도 사람의 신원을 식별하지 않고, 결과는 박스 좌표만 남는다.

7작업 큐와 API 렌더 게이트

NestJS와 Python이 같은 계약을 쓰도록 라이브러리 없이 Redis 리스트를 큐로 쓴다. 대신 "워커가 죽으면?"과 "Redis가 재시작되면?"을 직접 처리한다.

문제해결위치
워커가 메시지를 꺼낸 뒤 죽으면 작업이 사라지고 화면은 영원히 "처리 중" (리뷰 E1)꺼내면서 processing:worker에 옮기고 끝나면 LREM. 워커 시작 시 남은 항목을 원래 큐로 되돌림main.py pop_next(), requeue_processing()
긴 분석 뒤에 짧은 수동 박스 전파가 줄 서서 "추적 중"이 수 분 지속 (E3)확인 순서 propagate → render → analyzemain.py PRIORITY
Redis가 재시작되면 상태 해시가 사라짐 (E2)워커가 상태를 job:{id}:status 해시와 status.json 파일에 함께 기록, API는 해시가 없으면 파일을 읽음status.py StatusWriter.set(), jobs.service.ts
2GB 업로드를 메모리에 받으면 API가 죽음 (E4)multer diskStorage로 작업 디렉터리에 바로 기록, 실패 시 디렉터리 정리apps/api/src/jobs/upload.ts

렌더 게이트 (POST /api/jobs/:id/render)

API가 큐에 넣기 전에 순서대로 검사하고, 하나라도 걸리면 409를 돌려준다 (jobs.service.ts requestRender()).

  1. review.json 항목 중 edits.reviewed에 없는 것이 있으면 → "확인 필요 항목 N건이 남았습니다."
  2. 이미 렌더 중이거나, 렌더 요청 키(job:{id}:render_requested)가 워커의 마지막 상태보다 최신이면 → "이미 렌더 중입니다." (중복 클릭 방지)
  3. 상태가 ready/rendered가 아니면 → "분석이 끝난 뒤에 렌더할 수 있습니다."
  4. 통과하면 요청 키를 기록하고 queue:render에 {"jobId"}를 넣는다.

웹도 미처리 항목이 있으면 렌더 버튼을 끄지만, 최종 판단은 API가 한다. 화면을 우회해도 검수 없이 결과 파일이 나오지 않는다.
