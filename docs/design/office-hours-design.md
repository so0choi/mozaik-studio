- **구현 방식** (R1을 어떻게 만드나): **방식 A** 미리 분석 + 브라우저 오버레이 / **방식 B** 완전한 스튜디오 아키텍처 / **방식 C** 자동 처리 + 얼굴 갤러리만.

## Problem Statement
팀 내부 회의에서 다음 출시 기능 후보로 "영상 얼굴 자동 모자이크"가 나왔고, 블러미(BlurMe)의 Video Studio 같은 "모자이크 스튜디오"가 나온다고 윗선에 보고됐다. 연내(2026-12-31)에 경영진에게 보여줄 수 있는 프로토타입이 필요하다. 대상 서비스는 미디버스와 미디버스 커머스이지만, 프로토타입은 두 콘솔과 분리된 독립 웹 스튜디오로 만든다.

## Demand Evidence
- 외부 수요 증거 없음. 사용자 표현: "없어도 무슨일이 생기진 않지만 이미 위로 보고 돼서 최대한 기능이 만들어져야함".
- 고객 문의 이력 없음. 떠오르는 고객사 없음. 출발점은 경쟁 서비스(블러미) 기능 관찰.
- 따라서 성공 기준은 "고객이 쓴다"가 아니라 "보고된 내용과 일치하는 동작하는 데모"이다. 수요 검증은 프로토타입 이후 별도 과제.

## Status Quo
- 현재 미디버스/커머스에는 얼굴 모자이크 수단이 없고, 고객도 이를 요구한 적이 없다.
- 경쟁 기준점: 블러미 Video Studio — 업로드 → 서버가 모든 프레임에서 얼굴·번호판 검출 → 결과 검수(얼굴 클릭으로 보이기/숨기기) → 놓친 곳에 수동 박스(움직임 추적) → 재생 확인 → 다운로드. 파일 최대 10GB(요금제별), 일괄 처리는 Pro.
- 오픈소스 기준점: deface (MIT, CenterFace ONNX, CLI). 추적·편집 UI 없음, 오디오 제거됨.

## Target User & Narrowest Wedge
- 1차 "사용자": 데모를 보는 사내 의사결정자(보고 라인). 실제 고객 페르소나는 미정.
- 최소 범위: 영상 1개 업로드 → 자동 얼굴 검출·추적 → 얼굴 갤러리에서 사람별 켜기/끄기 → 놓친 영역 수동 박스 → 오디오가 보존된 결과 다운로드.

## Constraints
- 기한: 연내 프로토타입 (약 8주, 2026-10-30 기준).
- 독립 스튜디오이므로 인증·저장·내보내기를 스튜디오가 자체 처리.
- 사내 배포만. 외부 고객 공개 아님.
- **개인정보 범위:** 얼굴 인식을 하지 않으므로 생체정보(민감정보) 처리는 피한다. 그러나 실제 인물이 나오는 원본 영상과 얼굴 썸네일을 업로드·저장·표시하는 것 자체는 일반 개인정보 처리이므로 다음은 여전히 적용된다: 샘플 영상 촬영 대상자 동의, 작업별 접근 제어, 원본·썸네일 보관 기간과 삭제(아래 Storage 참고).
- **추적기 제약:** 추적은 위치·움직임(IoU, 칼만 필터)만 사용한다. 외형 임베딩/ReID 특징값을 쓰는 추적기(예: ReID를 켠 BoT-SORT, DeepSORT)는 사용하지 않는다. 이 제약이 깨지면 생체정보 회피 주장도 무효가 된다.

## Premises (사용자 동의 완료)
1. 목표는 연말까지 경영진에게 보여줄 "블러미 Video Studio급" 프로토타입이다. 외부 고객 수요는 아직 검증되지 않았다.
2. 미디버스/커머스 콘솔이 아닌 독립 웹 스튜디오로 만든다. 두 서비스 연동은 나중에 한다.
3. 핵심 흐름: 업로드 → 서버 얼굴 검출·추적 → 브라우저 검수(얼굴별 켜기/끄기, 수동 박스) → 서버 최종 렌더링(오디오 유지) → 다운로드.
4. "특정인 제외"는 얼굴(트랙)별 켜기/끄기로 해결한다. 얼굴 인식(R-Recog)은 프로토타입에서 빠진다.
5. 실시간 라이브(R-Live)는 스튜디오 프로토타입 범위 밖이다. 수요가 확인되면 별도로 결정한다.
6. 사내 배포만, 간단한 사내 인증. 번호판·배경 블러 등 부가 기능은 나중에.

## Key Insight
원래 로드맵에서 "특정인만 빼고 모자이크"는 얼굴 인식이 필요하다고 봤지만, 스튜디오 맥락에서는 추적된 얼굴(트랙)을 클릭해 켜고 끄는 것으로 같은 결과가 나온다(블러미도 이 방식). 얼굴 인식(R-Recog)은 "여러 영상에 걸쳐 같은 사람을 자동 제외"가 필요해질 때만 고려한다. 이로써 인물 제외 가치는 R1에 들어오고, 생체정보 처리 리스크는 빠진다(일반 개인정보 처리 의무는 남는다).

## Approaches Considered
- **방식 A: 미리 분석 + 브라우저 오버레이 미리보기** — 선택됨 (아래 상세).
- **방식 B: 완전한 스튜디오 아키텍처** (오브젝트 스토리지, GPU 워커 풀, 타임라인 트랙 병합/분할 편집기, 외부 API) — 제외: 연내 데모 불가(human ~3-4개월), 검증되지 않은 수요에 과투자.
- **방식 C: 자동 처리 + 얼굴 갤러리만** — 단독 방식으로는 제외(놓친 얼굴을 고칠 수단 없음). 대신 방식 A의 중간 마일스톤 M2로 흡수되어 **약속 범위에 포함**된다.

## Recommended Approach — 방식 A

### 구조
```
[브라우저 React 스튜디오]
   │ 업로드                    ▲ tracks.json + 정규화 영상(normalized.mp4)
   ▼                           │
[FastAPI API] ──enqueue──▶ [Redis 큐] ──▶ [분석 워커]
   │                                       ├ 업로드 정규화 (ffmpeg → CFR H.264 MP4)
   │                                       ├ 얼굴 검출 (YuNet 기본, GPU 있으면 SCRFD)
   │                                       ├ 추적 (ByteTrack, ReID 없음) → 트랙 ID
   │                                       └ 트랙별 대표 썸네일 + tracks.json 저장
   │ 편집 상태(edits.json) 저장
   ▼
[렌더 워커] normalized.mp4 + tracks + edits → 프레임별 모자이크 → H.264 인코딩 + 원본 오디오 mux → output.mp4
```

### 시간축 정합 (미리보기 = 결과의 전제)
- **업로드 정규화:** 업로드 직후 ffmpeg로 원본을 고정 프레임레이트(CFR, 원본 fps를 정수로 반올림, 예: 29.97→30) H.264/AAC MP4(`normalized.mp4`)로 변환한다. 해상도는 유지한다. 이 파일 하나를 분석·브라우저 미리보기·최종 렌더가 모두 사용한다. 가변 프레임레이트(VFR), HEVC, 브라우저에서 재생 안 되는 MOV는 이 단계에서 해소된다. 별도 프록시는 만들지 않는다.
- **프레임 인덱스:** tracks.json은 `normalized.mp4`의 프레임 번호(0부터)로 저장한다. CFR이므로 `frame = round(t × fps)`가 성립한다. 브라우저는 `requestVideoFrameCallback`의 `mediaTime`으로 현재 프레임 번호를 계산해 오버레이를 그린다(재생 시간 기반 setInterval 사용 금지).
- **오디오:** 정규화 단계에서 오디오도 함께 재인코딩해 `normalized.mp4`에 들어간다. 최종 렌더는 이 파일의 오디오 트랙을 그대로 복사(`-c:a copy`)해 mux하므로, 영상·오디오가 같은 타임라인을 공유한다.

### 노출 방지 규칙 (초기값, M1에서 샘플로 조정)
- **재현율 우선 검출:** 검출 신뢰도 임계값을 낮게 시작(YuNet `score_threshold` 0.5, 기본 0.9 대비). 잘못 가리는 것은 허용하고 놓치는 것을 줄인다.
- **박스 확장:** 검출 박스를 가로·세로 각각 25% 확장(중심 기준)해 머리카락·귀·턱까지 덮는다.
- **끊김 유지(gap-hold):** 트랙이 검출되지 않는 프레임이 생기면 마지막 박스를 최대 15프레임(30fps 기준 0.5초) 동안 유지한다. 보수적 ByteTrack 설정으로 끊김이 늘어나므로 이 규칙이 노출 방지의 핵심이다. 강제로 끊긴 트랙도 끊긴 지점에서 동일하게 유지한다.
- 이 세 값은 tracks.json 생성 시 적용되어 결과 박스 좌표에 이미 반영된다. 미리보기와 렌더는 같은 박스를 그대로 쓴다.

### 미리보기-결과 공간 정합
- **브라우저 미리보기:** `normalized.mp4` 재생 위에 canvas 오버레이를 겹쳐, ON 상태인 트랙·수동 박스 영역을 모자이크로 그린다. 켜기/끄기는 재처리 없이 즉시 반영된다.
- **공유 규칙 (단일 출처):** 박스 확장은 박스가 저장되는 시점에 단 한 번 적용한다(자동 트랙은 tracks.json 생성 시, 수동 박스는 CSRT 전파 결과를 저장할 때 같은 25%를 적용). 서버 렌더와 브라우저 오버레이는 저장된 박스 좌표(원본 해상도 픽셀)를 **확장 없이 그대로** 사용한다. `render_config`(tracks.json 안)에는 모자이크 블록 크기 규칙과, 기록용으로만 쓰는 확장 비율이 들어가며 소비자는 확장 비율을 다시 적용하지 않는다. 블록 크기 초기값은 박스 짧은 변의 1/8(최소 8px, 원본 픽셀 기준).
- **브라우저 환산:** canvas는 원본 좌표를 표시 크기 비율로 스케일해서 그린다. 블록 경계도 원본 픽셀 격자 기준으로 계산한 뒤 스케일하므로, 표시 크기가 달라도 가려지는 영역은 렌더와 같다.
- **정본:** 다운로드되는 `output.mp4`만 정본이다. 미리보기는 같은 규칙을 쓰는 근사치이며, 가려지는 **영역**은 일치해야 하고 모자이크의 픽셀 질감은 다를 수 있다.

### 얼굴 갤러리와 인물 제외 (트랙 조각·ID 뒤바뀜 대응)
- **기본값은 전부 모자이크(ON).** 사용자가 끈 트랙만 노출된다. 실수의 방향이 "과하게 가림"이 되도록 한다.
- **조각화를 ID 뒤바뀜보다 선호:** ByteTrack 매칭 기준을 보수적으로(높은 IoU 매칭 임계값) 잡고, 프레임 간 박스 중심 이동이 박스 크기 대비 크게 튀면 트랙을 강제로 끊는다. 한 사람이 여러 조각으로 나뉘는 건 허용하지만, 두 사람이 한 트랙에 섞이는 건 최대한 막는다.
- **갤러리 표시:** 트랙 조각마다 썸네일 카드 1장. 사용자는 여러 카드를 다중 선택해 "같은 사람"으로 묶을 수 있다(사람이 직접 묶는 수동 그룹화이며, 외형 비교는 하지 않는다). 그룹 단위로 켜기/끄기.
- **끄기 전 확인:** 트랙(또는 그룹)을 끄면 해당 트랙의 등장 구간이 타임라인 막대에 표시되고, 각 구간 시작·끝 썸네일을 함께 보여줘 다른 사람이 섞였는지 확인할 수 있게 한다.
- **최소 편집 동작(M3):** 트랙을 특정 프레임에서 **분할(split)**하는 기능 하나를 제공한다. ID가 뒤바뀐 트랙은 분할 후 해당 조각만 끄면 된다. 트랙 병합·키프레임 단위 편집은 방식 B 범위로 남긴다.
- **테스트:** 두 사람이 교차하는 장면과 가림(occlusion)이 있는 샘플 영상을 검증 세트에 포함하고, "끈 트랙에 다른 사람이 포함되지 않는다"를 확인한다.

### 수동 박스
- **생성:** 사용자가 일시정지한 프레임에서 박스를 그린다.
- **전파:** 서버에서 단일 객체 추적(OpenCV CSRT)으로 그 프레임 기준 앞뒤로 전파한다. 중단 조건은 추적 신뢰도 하락(추적 실패 반환) 또는 방향별 최대 10초 중 먼저 오는 것.
- **실행 방식:** 비동기 작업(큐). 전파 중에는 해당 수동 트랙 카드에 "추적 중" 표시가 뜨고, 그린 프레임에는 박스가 즉시 고정 표시된다. 끝나면 오버레이에 반영된다.
- **편집:** (1) 다른 프레임에서 박스를 다시 그리면 그 프레임을 새 기준점으로 재전파, (2) 시작·끝 프레임을 잘라 구간 축소(trim), (3) 삭제.
- **대체 수단:** 추적이 계속 실패하는 경우를 위해 "고정 박스 + 사용자가 지정한 구간" 옵션을 둔다.

### 저장소와 접근 (프로토타입 기본값)
- **위치:** 서버 로컬 볼륨 `/data/jobs/{job_id}/` 아래에 `original.*`, `normalized.mp4`, `tracks.json`, `thumbs/`, `edits.json`, `output.mp4`. 작업 메타데이터(소유자, 상태, 생성 시각)는 SQLite.
- **접근:** 사내 인증 사용자는 자신이 만든 작업만 조회·편집·다운로드한다. 다른 사람의 작업 ID로 접근하면 404.
- **보관/삭제:** 작업은 생성 7일 후 자동 삭제(디렉터리 전체 + 메타데이터). 사용자는 언제든 수동 삭제 가능하며, 삭제 시 원본·썸네일·결과가 모두 지워진다.
